# Release Tag Review Notes

## RTR-01: Stricter Ref And Stage-Payload Validation

Release-tag now validates release identities at shared boundaries, including direct library stages and dry-runs. Invalid identities fail before Git mutations or GitHub requests. When a base branch must be read from Git, orchestration validates that result before authentication preflight.

- Base and release branches must be short Git branch names. Leading options (`--mirror`, `-D`), full `refs/*` aliases, refspecs such as `main:other`, traversal/dot components, `.lock` components, control characters, and other invalid Git ref syntax are rejected. `HEAD` is rejected; the existing base-branch guard also rejects `vX.Y.Z` tag shapes. Ordinary nested and Unicode names remain supported.
- Base and release branches must differ, including generated `changelog/<version>` branches. Supply a distinct release branch rather than an alias for the base.
- `GITHUB_REF_TYPE=tag` or `GITHUB_REF=refs/tags/*` prevents inferring a base from `GITHUB_REF_NAME`, including non-version tags such as `latest`. Diagnostics direct callers to check out the intended branch and provide `--base-branch`. An explicit base retains precedence; determine-only runs do not infer a base.
- Environment branch/repository values are validated as supplied. Leading/trailing whitespace is no longer silently trimmed. Git ref output accepts a single line ending; padded values and extra lines are rejected.
- Stable numeric version components must be between `0` and `9007199254740991`, inclusive. Manual `v1.2.3` still normalizes to `1.2.3`; leading zeros, prereleases, and build metadata remain unsupported. Unsafe latest-tag components fail before reading commit history.
- Direct stage payloads must have the documented field types. `determined.tagVersion` must equal `v` plus `determined.version`, and a supplied plan tag must match that version. PR payload branches must match the explicit/environment base when present and the configured release branch or default `changelog/<determined.version>`. Custom release branches remain supported through `releaseBranch` in the plan.
- Explicit `githubRepository` and the `GITHUB_REPOSITORY` fallback must contain exactly two nonempty components using ASCII letters, digits, dots, underscores, or hyphens. Dot segments (`.` or `..`), encoded routing shapes, backslashes, query/fragment delimiters, and control characters are rejected.

RTR-06 also validates automatic bump outputs inside determination itself; see the [version-policy notes](#rtr-06-conventional-commit-boundaries-and-no-change-releases). Unsafe generated versions fail before preflight or release operations.

## RTR-02: Verified Source Preparation And Release Postconditions

Release preparation now checks repository state before writing Git configuration or changing branches. These corrections intentionally replace destructive branch resets and missing-command success.

- Check out the selected **local** base branch with a clean tracked/untracked worktree. An explicit or environment base does not authorize releasing another branch at the same commit, a detached HEAD, or a tag checkout. Missing bases and HEAD/source mismatches fail with checkout guidance. Branch creation uses the verified source commit explicitly; it never switches to or resets the base on the caller's behalf.
- Existing local or remote release branches are refused by default. Library callers can explicitly set `resetReleaseBranch: true` (default `false`) for an inspected, intentional restart. Local reset uses `checkout -B` from the verified source, retaining the release branch's reflog. The remote branch is updated in place using `--force-with-lease=<full-release-ref>:<observed-object-id>`; a new branch uses an empty expected ID to require remote absence. Refreshed remote-tracking refs cannot silently relax this lease. No blind branch deletion or unconditional force push remains.
- Local symbolic branch refs (including dangling aliases omitted by ordinary ref listings) and remote-advertised symbolic aliases are refused before configuration/reset. Distinct short names alone are insufficient: Git can follow a symbolic release ref during `checkout -B` and otherwise move the base.
- Executed releases require an available command before preparation. A path must resolve to an executable regular file; a bare name must pass its bounded `--version` availability probe. Missing, non-executable, and failed-probe commands now fail with install/configuration guidance instead of returning success after pushing a branch.
- A new release is refused when its target tag exists locally or on origin, including lightweight and annotated tags. `resetReleaseBranch` does not override tag immutability. Choose a new version rather than deleting or overwriting a release tag. `skipRelease` deliberately permits existing tag metadata for preparation/composition.
- A zero exit from the release executable is insufficient: the expected release branch must still be checked out, the tracked/untracked worktree must be clean, and the target tag must resolve to HEAD. Missing/mismatched tags, branch switches, detached HEAD, or pending changes stop the package's final push and all downstream PR work.
- Successful executed releases add optional `ReleaseBranchResult.releasedHead`, the full verified commit ID. Final branch publication uses that exact commit and a lease on the prepared source, also accepting a branch already published at the same head by the executable. Package-owned branch pushes use explicit refspecs and disable implicit tag following. The release executable owns tag publication. RTR-05 will consume this head for PR merge pinning.
- `skipRelease: true` remains a selected preparation stage: clean-source checks, collision policy, author configuration, branch creation/reset, an upstream push, and annotation reading still occur. It skips command availability, new-release tag checks, and executed-release postconditions, and does not claim a `releasedHead`. Legacy manually supplied stage results can omit the additive field; a supplied value must be a full Git object ID.
- A directly invoked release stage excluded by `only` now returns `skippedReason: 'stage not selected'` with zero process, filesystem, or network operations. Like direct-stage dry-run, it requires an explicit `baseBranch` or `GITHUB_REF_NAME`; it will not read Git to infer a missing base. Top-level `only` still returns `null` for excluded stages.

Preparation and external executables are not transactional. A failed lease or later release step can leave a local prepared branch (including an explicitly authorized local reset), and the initial upstream branch may already exist. Inspect that state before retrying. Postcondition checks gate the package's final push/PR, but cannot undo pushes or other side effects performed by the executable. Serialize release jobs and avoid concurrent local Git writers; source validation and postcondition reads do not create a repository-wide lock. No release-tag overwrite is an automatic recovery action.

The reset option is library-only at this step; RTR-07 owns its CLI flag. RTR-03 owns bounded release-process transport, RTR-05 owns PR recovery/head pinning, and RTR-08 owns the complete guide/migration examples.

## RTR-03: Bounded Captured Process Execution

Release-tag now owns its asynchronous subprocess transport. All Git reads/mutations, bare-command availability probes, and release execution pass through one package-local capture/error boundary; the shared runner used by other packages is unchanged.

- `timeoutMs` defaults to 60,000 ms per invocation and accepts only integers from `1` through `2147483647`, the Node timer-supported range. Availability probes remain capped at `min(timeoutMs, 10000)`. The deadline stays active through pipe closure, including when the direct child has exited but descendants retain its pipes.
- `maxOutputBytes` defaults to 1 MiB and remains a positive safe integer. It bounds **combined raw stdout and stderr bytes while streaming**, before UTF-8 decoding. On overflow, at most that many output bytes are retained, the readers close, and the producer is terminated. Storage uses bounded blocks rather than one allocation per tiny write; pipe/read buffers, partially filled blocks, and decoded strings add bounded overhead. Invalid UTF-8 is decoded with replacement characters, whose encoded size can exceed the original raw-byte count. No RSS or speedup claim is made.
- Package-owned children have ignored stdin and captured stdout/stderr. Successful child logs are not forwarded, so a noisy release executable cannot corrupt JSON stdout. Failures report the operation, status or safe transport-error classification, elapsed time, and up to 2 KiB of diagnostic text (plus labels/truncation markers). Git stdout is excluded from errors to avoid dumping commit bodies or configuration values; release/probe stdout may supply a bounded diagnostic tail. Overflow diagnostics use only the retained prefix. Raw transport messages, stacks, and causes are not attached to new process errors. The boundary accepts supplied redaction values and the configured token environment; RTR-04 owns the full credential-context/redaction work.
- Timeout/overflow sends SIGTERM, then SIGKILL after a 250 ms grace period. POSIX children run in their own process group, so ordinary children/grandchildren are signaled too, even after the group leader exits. The transport waits for direct-child reaping and pipe closure, with another 1 s cleanup allowance after escalation. If termination cannot be confirmed, it reports that condition and stops waiting. Arbitrary processes escaping the group, OS-uninterruptible tasks, and non-POSIX process-tree cancellation are outside this guarantee; adopted descendants rely on the OS to reap them. Non-POSIX cancellation targets the direct child and closes retained pipes at the cleanup deadline.
- Every Git/release child receives `GIT_TERMINAL_PROMPT=0`. Existing `GIT_SSH_COMMAND`, `GIT_SSH`, and `core.sshCommand` identities are preserved; the built-in transport treats empty SSH environment overrides as unset. Only preflight probes SSH configuration to decide whether to supply its default batch-mode command; later Git operations do not repeatedly reprobe it. Failed SSH-configuration probes now stop preflight instead of falling through after an unexpected process failure.
- Custom `CapturingProcessRunner` objects remain supported, but release execution now calls **`capture` rather than `run`**. Implementations receive explicit argument arrays, `cwd`, `timeoutMs`, `stdio: 'pipe'`, environment overrides, and additive `maxOutputBytes`. They must implement their own streaming bounds, environment merging, deadlines, termination/reaping, and stdout isolation. Completed results must contain stdout/stderr strings, an integer or null exit code, and an optional Error; malformed, oversized, or late results fail at the boundary. Byte checks on custom strings use their UTF-8 encoding. A wrapper cannot cancel an arbitrary injected promise or preempt synchronous code, and post-completion checks do not bound memory already allocated by a custom runner. Custom errors retain allowlisted error-code classifications rather than arbitrary messages/causes; return useful failure diagnostics in captured stderr.

Limit flags remain assigned to RTR-07. Process termination cannot undo release-command side effects or the initial prepared-branch push; the RTR-02 partial-failure guidance still applies.

## RTR-04: Private Credentials And Bounded GitHub Transport

- HTTP response consumption now streams raw bytes, retaining at most `min(maxOutputBytes, 1048576)` bytes before decoding. Overflow cancels the reader and aborts the request without consuming the full producer. One `timeoutMs` deadline covers fetch and body reads, including stalled streams and empty-chunk producers. Reader cancellation failures are discarded; cleanup is requested without waiting indefinitely for a custom cancellation promise. A transport `AbortError` is reported as an abort, rather than falsely claiming the configured deadline elapsed; transport `TimeoutError` and actual elapsed deadlines remain distinguishable.
- Authenticated fetches use `redirect: 'error'`; returned redirects from custom transports are also rejected before reading their bodies. API bases must use HTTPS, except HTTP on numeric loopback addresses (`127.0.0.0/8`, `::1`) or literal `localhost`. Userinfo, queries, fragments, control characters, backslashes, and ambiguous encoded/dot routing paths are rejected. Endpoint construction retains GHES base prefixes and encodes individual path segments; only package-constructed endpoint queries are appended. Plan resolution now owns `githubApiUrl` > `GITHUB_API_URL` > `https://api.github.com` precedence, equally for CLI and library callers.
- Token files have a fixed **65,536-byte cap**, including whitespace. The reader opens nonblocking, verifies the opened target is a regular file, checks its size, and reads at most **65,537 bytes** to detect growth after inspection. Symlinks to regular files remain usable; directories/FIFOs and other nonregular targets fail. File contents must be ASCII and trim to one bearer token using letters, digits, `._~+/-`, with optional trailing `=` padding. Empty, oversized, invalid-header, unreadable, and nonregular files fail without environment fallback. Explicit tokens take precedence without reading the file; explicitly empty/invalid tokens now fail. An empty environment variable remains unavailable.
- Each orchestration has its own private, lazy credential context, with no global execution registry or raw credential in a plan. The active token is pinned once and reused for preflight, release diagnostics, PR requests, and errors even after file/environment rotation. Determination precedes file resolution; dry-run and unselected/skipped PR credential paths never open token files. While a configured file credential remains unresolved, process failures omit captured output while retaining operation guidance and exit/transport classification. RTR-06 can return after no-change determination before entering this credential boundary.
- Exported direct stages use the same error boundary. `DetermineNextTagInput` and `RunReleaseBranchInput` add optional `githubToken`, matching the preflight/PR inputs; supply it at each direct stage when using an explicit token. Plan resolution never stores that token for later use. New errors retain bounded, sanitized messages and standard error classifications, with fresh sanitized stacks and no raw causes, custom properties, or recursive traversal of caller-owned transport objects. Filesystem errors expose a controlled I/O classification rather than raw paths/messages.
- Output snapshots, tag annotations, PR titles/descriptions, and returned PR URLs redact known explicit/default/configured-environment values and the resolved active file token, including ordinary URI/JSON-escaped echoes and URL userinfo. Redaction applies before diagnostic truncation. Operational Git executables/arguments, source refs, and PR head/base identities stay unchanged. Excluded token files are not inspected to discover otherwise unknown secrets. Returned orchestration plans contain data only; execution-plan transports are nonenumerable, and JSON/inspection uses a resolved-time safe snapshot. The operational plan is for execution, while sanitized returned snapshots are for reporting; a deliberately token-overlapping identity may be redacted in reporting data.
- Custom fetch implementations must return standard `Response` byte streams, honor the redirect policy and `AbortSignal`, and own their underlying socket/producer cleanup. The boundary stops waiting at its deadline and cancels a late response, but cannot undo credential forwarding or arbitrary side effects performed inside an injected transport, preempt blocking JavaScript, or bound memory it allocated before delivering a chunk. The byte cap excludes the current transport-provided chunk, transport buffering, and bounded decoding overhead; no RSS or speedup claim is made. Existing SSH identities and installation-token preflight probes remain supported.

PR reuse/merge semantics, CLI parse-handler restructuring, and complete guide examples remain assigned to RTR-05, RTR-07, and RTR-08 respectively. These notes describe the credential/transport contract independently of those pending changes.

## RTR-05: Recoverable PR Lifecycle And Verified Merges

- Stage 3 now discovers PRs with `GET /repos/{owner}/{repo}/pulls?state=all&head={owner}:{releaseBranch}&base={baseBranch}&per_page=2&page=1`. It requests two records so ambiguity fails without scanning arbitrary pages; it never follows response-provided pagination URLs. Multiple matches, including an open and an older closed PR for the same refs, require inspection rather than an automatic selection. Repository names follow GitHub's case-insensitive identity semantics; branch names remain case-sensitive.
- List records supply the number, URL, refs, repository identities/IDs, state, and head SHA. The real list shape does **not** supply the detail endpoint's `merged` boolean. An existing match always receives a detail read before mutation or merge confirmation; a list `merged_at` timestamp alone is not proof of a merge. Returned head and base repositories must match the configured repository and each other, including repository IDs. Cross-repository/fork heads, missing/deleted repository metadata, changed PR numbers/repository IDs, and mismatched branch identities are refused. Create and update responses receive the same identity checks; a number/URL alone no longer suffices.
- An absent PR is created with the existing title/body template. A matching open PR is reused and its title/body updated without retargeting its base. Labels `changelog`, `release-candidate`, and `<tagVersion>` are reapplied on every successful attempt, including already-merged recovery. `PullRequestResult.reused` is `true` for a discovered or concurrently created PR, `false` for an initial creation or skip. A closed-unmerged match fails with guidance to inspect and reopen that PR or choose a new release identity; it is not silently replaced or reopened.
- A create HTTP 409 or 422 permits **one** identical bounded relookup to recover a concurrent creation. If there is still no exact match, the operation fails with the original create status. No other failed requests trigger automatic retries or further discovery. Each execution makes at most two list requests, at most two detail reads, and at most one each of create, update, labels, merge, ref read, and deletion: **ten HTTP requests maximum** on the complete conflict/merge/cleanup path. Each retains RTR-04's streaming byte cap, deadline, redaction, and redirect policy.
- `mergeMethod?: 'merge' | 'squash' | 'rebase'` is a validated library option, defaulting to `'merge'`; `ReleaseTagMergeMethod` is exported and plan snapshots retain the choice. Its CLI flag is scheduled for RTR-07. `autoMergePr` remains an **immediate REST merge**, not queued auto-merge, approval automation, or a merge queue. Repository protections, required reviews/checks, authentication, and unsupported methods can still reject it and are reported as actionable errors.
- Before a requested merge, a fresh detail read must retain the selected PR number, repository IDs, base/head refs, and head SHA. Every observed PR head must match `ReleaseBranchResult.releasedHead` when supplied. The merge request sends `{ merge_method, sha }`; a changed head after the last read is guarded by GitHub's SHA precondition. Legacy/preparation-only release metadata can omit `releasedHead`; those calls pin the first validated API head without claiming stage-2 verification. Only a successful response with literal **`merged === true`** confirms a merge; false, missing, string/numeric values, malformed JSON and failed responses stop cleanup. A lost merge response is uncertain until a later execution confirms the exact PR's detail state.
- An exact already-merged PR returns `merged: true` without another merge or title/body update. With both `autoMergePr` and `deleteMergedBranch`, cleanup can resume after label/deletion failure. Cleanup first reads the singular `GET /git/ref/heads/{releaseBranch}`, checks the exact full release ref (never the base), requires a commit object, and compares its SHA to the validated merged release head. A changed/ref-mismatched response refuses DELETE. HTTP 404 on this post-confirmation ref read is treated as already absent, including GitHub-owned auto-deletion; `branchDeleted: true` describes the confirmed-absent or acknowledged-deletion outcome, not necessarily deletion performed by this invocation. Other read failures stop cleanup. DELETE must return the documented 204; a failed/lost DELETE response can be recovered by the next execution's absence check.
- **REST branch cleanup is not an atomic compare-and-delete.** GitHub's DELETE-ref endpoint provides no SHA lease. A concurrent writer can change or recreate the ref after the GET check and before DELETE, and that new ref can still be deleted. Serialize release jobs and avoid concurrent ref writers; these checks cannot provide a distributed transaction or lock. As with GitHub's normal API behavior, a ref 404 cannot independently distinguish absence from a newly inaccessible resource. The preceding authenticated PR reads and successful label operation provide context, but cannot eliminate a simultaneous access-policy change.
- Partial-failure diagnostics identify the safe PR number/URL and failed lifecycle stage once that identity has been validated. They include guidance to resume `createReleasePullRequest` with the existing verified `determined`/`release` metadata, which rediscovers the PR and reapplies labels. Failed creation/body parsing can leave the remote outcome uncertain; its diagnostic calls for inspecting the exact identity before resuming. Errors retain sanitized classifications and bounded messages with no raw response objects, caller properties, causes or token-bearing stacks. Known credentials are also redacted from returned URLs and updated descriptions; operational ref identities remain unchanged.

Recovery at this step is the direct library PR stage. RTR-07 owns PR-only orchestration/CLI composition and flags; RTR-08 owns the complete guide and CI examples. These changes preserve the existing skip/dry-run no-network/no-token-file-read boundaries, credential pinning, and annotation/signature/label contracts.

## RTR-06: Conventional Commit Boundaries And No-Change Releases

Automatic version policy now recognizes individual commit headers and breaking footers. The old shell-regex matches across concatenated messages are intentionally corrected, with no compatibility aliases for incidental punctuation or body feature examples.

- Git output uses `git log <lastTag>..HEAD -z --format=%H%x00%B`: each record is `<full-commit-ID>\0<raw-message>\0`. The ID remains present for an empty-message commit, which receives the normal patch decision; an empty range has zero records. Both full SHA-1 and SHA-256 IDs are accepted. Malformed/truncated records fail without exposing message contents. Custom/fake capturing runners must return this record format instead of concatenated `%B` strings.
- The first raw message line is the header; following lines are the body. Using raw messages avoids Git `%s` folding a multiline first paragraph into an apparently valid header. `type(scope)!: description` permits an optional nonempty scope and an optional `!` immediately before the colon. Types use word characters with optional hyphens, without a leading hyphen; no type allowlist is imposed. Type matching is case-insensitive, so `FEAT` also gives minor. Headers require a space/tab after the colon and a nonempty description on that line. Any such type with `!` gives major, including `refactor!`, `chore(deps)!`, and custom types.
- Breaking footer markers must start at column zero in the **body**, use uppercase `BREAKING CHANGE:` or `BREAKING-CHANGE:`, and have a space/tab followed by a nonempty description on the same line. Inline/indented examples and footer-like subjects do not qualify. Body `feat:` or `refactor!:` examples are not headers; `fix: handle a!:b` gives patch, and `feat(scope!:example): add support` gives minor. Across all records, major wins over minor, then patch. A breaking footer can mark a commit whose subject is not conventional.
- `ReleaseTagOptions.allowEmptyRelease?: boolean` defaults to `false`; resolved plans and their safe snapshots contain `allowEmptyRelease: boolean`. `DeterminedTag` adds required `noChanges: boolean`, including for manually supplied direct-stage payloads. `bump: null` now covers both manual requests and no-change results, so consumers must use `manual`/`noChanges` to distinguish them:

  | Determination                                      | Version/tag                  | `bump`                       | `manual` | `noChanges` |
  | -------------------------------------------------- | ---------------------------- | ---------------------------- | -------- | ----------- |
  | Manual `tag`                                       | Normalized requested version | `null`                       | `true`   | `false`     |
  | Automatic, commits present                         | Classified next version      | `major`, `minor`, or `patch` | `false`  | `false`     |
  | Automatic, zero commits, default                   | Current version and last tag | `null`                       | `false`  | `true`      |
  | Automatic, zero commits, `allowEmptyRelease: true` | Next patch version           | `patch`                      | `false`  | `false`     |

- A no-change `runReleaseTag` returns the safe determined result with `release: null` and `pullRequest: null`. It performs only the two local determination reads, bypassing preflight, environment base/repository inference, worktree/ref checks, command availability, token-file resolution, release execution, and PR work. This permits an unchanged tagged/detached or dirty checkout to return successfully without needing a base branch, origin, executable, or readable token file. Pure explicit-plan validation still applies. Runtime identity validation remains mandatory before downstream work on an actual release. Direct-stage composition should honor `determined.noChanges` before explicitly invoking those stages.
- Manual `tag` values remain explicit release requests, independent of `allowEmptyRelease`, with **zero Git reads during determination**. Their later stages retain normal source/tag/credential checks. To deliberately release an empty range, library callers can set `allowEmptyRelease: true`; this opts into the previous patch increment, not into weaker release validation.
- Bump outputs must still be exact stable versions with safe-integer components (`0` through `9007199254740991`). An increment beyond a component's limit fails inside determination before token reads, authentication, or mutation; it is not rounded, wrapped, or promoted to another bump. Ordinary decimal carries and resetting lower components for minor/major bumps remain valid. A no-change or manual version at the safe limit is valid because no increment is attempted.
- Latest-tag selection still uses `git describe --tags --abbrev=0` and requires strict stable `vX.Y.Z`. Missing history retains `Provide --tag once to seed release history.` guidance. Reinterpreting unrelated tags, prerelease channels, and configurable tag prefixes remain deferred.

The no-change/result contract is established here. RTR-07 completes `--allow-empty-release`, CLI plan/text formatting, and the JSON schema/version decision; the existing JSON result serializer already carries `determined.noChanges`. RTR-08 owns the complete website guide and migration examples.

## RTR-07: PR-Only Recovery And Thin CLI

- `only: ['pr']` with explicit `tag` and `baseBranch` (CLI `--only pr --tag X.Y.Z --base-branch main`, including dry-run) runs read-only recovery: manual determination without Git reads, `changelog/<version>` derivation or an explicit release branch, a pinned local tag-object read, commit resolution, signature-stripped annotation extraction, and local plus `origin` release-ref checks. Lightweight tags contribute their commit message; annotated tags contribute their annotation. Remote-only branches work from a fresh checkout without a local base or release branch, and dirty/detached checkouts are preserved. Local symbolic aliases (including dangling aliases), remote-advertised aliases, tag aliases, non-commit tags, moved tags, and local/remote head mismatches fail before any HTTP or Git mutation.
- Recovery never runs `config`, `checkout`, `reset`, `push`, `fetch`, `branch`, `tag`, or `update-ref`, never creates refs, and never runs the release executable, regardless of `resetReleaseBranch`, `signCommit`, or `allowEmptyRelease`. It does not fetch or reconstruct refs. An absent `origin` release branch is accepted only when the verified local tag head and the exact already-merged PR at that commit support RTR-05's already-deleted cleanup no-op; absent/open/closed-unmerged/wrong-SHA/wrong-base/ambiguous/list-only-merged cases fail before any write API. Unknown plan keys such as `allowMissingBranch` are ignored and cannot bypass this gate; the internal verified-absence evidence is a frozen object-identity check, not a flag.
- Other stage subsets still fail before I/O, including in dry-run: `release` without `determine`, and `pr` without both `determine` and `release` except the explicit recovery form. Dry-run, `skipPr`, and missing-token recovery paths perform zero Git, token-file, and network work; no-change orchestration still performs only determination reads. Recovered `determined`/`release` identities stay internal; the orchestration result reports `determined: null` and `release: null` for unselected stages and the idempotent PR result.
- New CLI flags use shared `parseFlags`: repeatable raw `--release-arg` (commas preserved; dash-leading values require `--release-arg=--flag`, while the space form rejects them as missing values), strict `--timeout-ms` (`1..2147483647`) and `--max-output-bytes` (positive safe integers) with digits-only/no-leading-zeros/no-blank validation matching plan limits, `--reset-release-branch`/`--no-reset-release-branch`, `--allow-empty-release`/`--no-allow-empty-release`, and `--merge-method merge|squash|rebase`. Existing aliases (`--release-it-path`) and `--sign-commit` negation keep last-writer semantics.
- `src/cli.ts` is a thin entrypoint that only parses, executes, formats, and sets `process.exitCode`; import-safe `src/cli-options.ts` and `src/format.ts` own flags/secrets and help/JSON/text rendering. Tests import those helpers rather than the executable module. Parse/build failures redact every inline `--github-token` value (space/equals, including overridden repeats) plus `GITHUB_TOKEN` and referenced custom-env values before printing.
- `--json` emits exactly one schema-1 object with no uncontrolled child stdout for full releases, noisy failures, no-change runs, and recovery. Schema 1 is retained because RTR-02 through RTR-07 only add optional or backward-compatible fields (`releasedHead`, `reused`, `noChanges`, `allowEmptyRelease`, `resetReleaseBranch`, `mergeMethod`, existing limit fields); no established field changed type or meaning. Text output reports recovery mode, `noChanges`, `releasedHead`, `reused`, and skipped (no changes) states coherently with the JSON result.

## RTR-08: Consolidated Guides And Final External Contract

RTR-08 is docs-only and changes no code contract. It rewrites the website guide to the finished behavior, keeps the package README concise with pointers here, and extends the dispatch notes with serialization and recovery guidance. Root `CHANGELOG.md` remains untouched by design; these notes are the release-notes record for the remediation.

- Final CLI surface: `--tag`, `--cwd`, `--base-branch`, `--release-branch`, `--git-executable`, `--release-command`/`--release-it-path`, repeatable raw `--release-arg`, `--timeout-ms`, `--max-output-bytes`, `--git-user-name`, `--git-user-email`, negatable `--sign-commit`/`--reset-release-branch`/`--allow-empty-release`, `--github-token`/`--github-token-file`/`--github-token-env`, `--github-repository`, `--github-api-url`, `--auto-merge-pr`, `--merge-method merge|squash|rebase`, `--delete-merged-branch`, `--skip-release`, `--skip-pr`, `--skip-preflight`, repeatable comma-split `--only`, `--dry-run`, `--json`, `-h`/`--help`. Defaults: `release-it` path, `github-actions[bot]` identity, `60000` ms deadline, `1048576`-byte cap, `merge` method, everything else off/derived. Review the built `--help` output before release use; the website guide's flag table, dry-run summaries, and JSON envelope were checked against it.
- Final schema-1 result shapes: `determined` is `{ version, tagVersion, bump, lastTag, manual, noChanges }`, `release` is `{ baseBranch, releaseBranch, releaseRan, releasedHead?, skippedReason, tagMessage, prTitle }`, and `pullRequest` is `{ skipped, skippedReason, number, url, reused, merged, branchDeleted }`, with `null` for unselected stages and skipped results for selected-but-skipped stages. Dry-run JSON adds `dryRun: true`.
- Final public exports: `resolveReleaseTagPlan`, `runReleaseTag`, `determineNextTag`, `runReleaseBranch`, `createReleasePullRequest`, `runPreflight`, `formatPullRequestBody`, and the `ReleaseTagOptions`, `ReleaseTagPlan`, `ReleaseTagResult`, `ReleaseTagStage`, `ReleaseTagMergeMethod`, `ReleaseTagTokenSource`, `DeterminedTag`, `DetermineNextTagInput`, `ReleaseBranchResult`, `RunReleaseBranchInput`, `PullRequestResult`, `CreateReleasePullRequestInput`, `PreflightResult`, `PreflightCheckResult`, `RunPreflightInput` types. Direct stages take an optional `githubToken` on their stage input; plan resolution never retains it.
- Custom transport responsibilities, consolidated: injected runners must serve every invocation through `capture` with their own streaming bounds, deadlines, termination, and stdout isolation; injected fetches must return standard `Response` streams, honor redirect policy and `AbortSignal`, and own socket cleanup. The package validates completed shapes/bytes/elapsed time and sanitizes diagnostics, but cannot preempt custom code, bound custom-allocated memory, or undo custom side effects such as credential forwarding.
- Residual races, consolidated: prepared-branch work can survive later failure; release executables own their side effects; REST GET-ref/DELETE cleanup has no SHA lease; a ref 404 cannot distinguish absence from an access-policy change; tag/branch moves after inspection rely on later head checks; source validation is not a repository-wide lock. Serialize release jobs with a concurrency group and `cancel-in-progress: false`, and recover with `--only pr` rather than rerunning releases or deleting tags.
- Preflight limits, consolidated: the Git probe proves non-interactive read access and the token probe proves readability plus installation identity; neither proves every endpoint write permission nor prevents later authentication failures. GitHub enforces each write at request time.
